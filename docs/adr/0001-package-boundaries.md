# ADR-0001 主包身份与渐进模块边界

- 状态：Proposed
- 日期：2026-11-04
- 关联需求：FR-002、FR-003
- 替代关系：无

## 背景与驱动因素

用户明确主 npm 包名为 `@adui/three`，这一名称是已确认事实（Accepted）。当前主包代码不存在；旧版混合通用三维能力与 Vue、Store、解密和业务路径，直接复制难以复用。截图给出多个未来扩展包作为参考，未要求一次实现。

本 ADR 整体状态 Proposed 专指以下架构方案，不能用它否定已确认的包名，也不能视为用户已批准所有边界。

## 候选方案

1. 所有能力装进单个巨型类：迁移直观，但可选依赖、生命周期和可测试性难管理。
2. 起步即创建 utils/effects/controls/gis/editor/vue/react 等多包：隔离明确，但未验证需求时带来版本、构建和发布成本。
3. 单主包、内部组合模块、按需拆分：先验证最小核心，在边界稳定后抽出功能包。

## 建议决策与理由

建议方案 3，主包未来放 packages/three，演示继续放 apps/website；现有 utils 模板不强行改造成主库。宿主只组织生命周期，业务路径和应用鉴权留消费端。框架适配可后续独立提供；Three.js peer dependency、版本和 exports 另行决策。

## 利弊与风险

收益是减少初期发布矩阵并保留演进空间；代价是需要控制主包内部依赖与导出，后续拆包仍有兼容成本。若 MVP 要求大量独立加载能力，需要重新评估模块划分。命名可用性与 npm scope 权限尚未核验，本轮不访问发布凭据或发布。

## 后续与维护

下一步选择首个使用场景、MVP、版本和 API 风格，再决定是否接受本方案。接受后更新状态并注明证据；重要替代方案新增 ADR 关联本记录，不抹除历史。架构索引位于 [ARCHITECTURE](../ARCHITECTURE.md)。
